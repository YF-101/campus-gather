# 真实产品首版

目标从作品展示转为小范围真实活动使用。首版需要陌生用户自助注册/登录/恢复账号、账号报名与取消、活动所有者发布和签到，数据经服务端保护并持久化。

## 本次实施顺序

1. 补认证流程：验证码失败可重试、过期可重新发送；显示正在验证的邮箱；密码恢复；认证成功但资料初始化失败可单独重试；不展示原始平台错误正文。
2. 所有者已选择：任何注册用户都能发布自己的活动。新迁移允许有效账号发布，名单与签到仍严格检查活动所有者；不修改账号角色或 RLS。云端滚动 24 小时最多发布 5 场，限制按用户行锁串行计算。
3. 增加发布者取消活动及原因、保留历史记录、停止取消活动的新报名和签到；云端页面每 30 秒在可见时更新，聚焦/联网时刷新。准备独立真实账号联合验收。
4. 验收实际新邮箱注册 → 登录 → 报名 → 组织者名单 → 签到，以及取消、权限拒绝和手机使用。必须由邮箱持有人输入验证码与真实密码，不读取浏览器凭据或替用户验证身份。
5. 通过后再将真实入口作为小范围试运行入口。备份、服务额度与告警需检查实际配置；不能把免费共享测试环境称为无限制或长期稳定服务。

## 本次认证设计

延续现有 CloudBase 官方 SDK，不更换云供应商、不购买服务、不新增认证方式、不放宽 RLS。`src/lib/cloud/auth-flow.ts` 负责输入、SDK 回调和资料准备；`cloud-auth-form.tsx` 负责表单、重发倒计时及反馈。临时回调和输入仅在页面内存，不写浏览器持久存储或项目文件。

密码恢复使用 SDK `resetPasswordForEmail` 返回的更新回调，由用户本人填写验证码和新密码。界面提示云账号与原时光小屋共用；开发验证仅使用虚构服务响应，不实际更改用户密码。

本地前端冷却只能防误点，不能代替云端发信限额与服务端防滥用。平台邮箱验证状态历史问题不通过伪造字段解决。

## 验证计划

- 先写失败测试，覆盖注册、密码/验证码登录、恢复、未建立会话、验证重试与资料准备重试。
- 运行逻辑、SQL、类型和构建检查；浏览器用无云凭证的可控测试夹具检验 UI，不把夹具入口放进正式构建。
- 线上验收的真实验证码由邮箱持有人输入；未完成前不宣称产品已经可以向所有陌生人开放。
